# Project Harness design contract

An adopted project has one portable collaboration entry, `HARNESS.md`, and uses the team's existing sources. The agent chooses its development methods. The [skill](../skills/project-harness/SKILL.md) covers adoption, reconciliation, handoff and release questions. Everyday work follows the project's own instructions.

## File behavior

Create a map only on adoption. Append links when their role is confirmed. Preserve existing agreements, historical records, identifiers and team instructions. Legacy Protocol 2 mappings remain readable. New maps use ordinary Markdown. Repeating an identical request adds nothing. Check the links the project declares, including a declared path that has since disappeared. Optional categories may be absent.

## Handoff and release evidence

Trace a handoff to the files its recipient can access. For a Git handoff compare the working map and declared records with the actual recipient revision. Keep release facts in the existing project source, including package identity, target environment, last verified deployment and data compatibility when returning to an older version.

## Maintainer verification

Exercise both native command families with empty projects, existing custom maps, legacy links, repeated adoption, broken paths and different Git snapshots. Verify representative project outcomes and keep example fixtures free of private project material.
